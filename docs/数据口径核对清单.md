## 一、已发现的错误（建议立刻按行业标准改）

### ❌ 1. 推广 CTR——必须改加权，算术均值是错的

| 项 | 算法 | 4 月数 |
|---|---|---|
| 行业标准（万象台后台用） | `SUM(总点击) / SUM(总展现)` | **3.67%** |
| 之前的算法（店长指定） | 每个商品 CTR 取算术平均 | 估算 ~5%（偏高 30%）|

**为什么算术平均错了：**
> 假设：A 商品 1000 曝光 3 点击 = 0.3% CTR；B 商品 10 曝光 1 点击 = 10% CTR
> 算术平均：(0.3 + 10) / 2 = **5.15%**（B 这种小数据被放大权重）
> 真实 CTR：(3 + 1) / (1000 + 10) = **0.40%**
>
> 投放决策上：算术平均会让我们误以为 CTR 健康，实际上 99% 的曝光对应 0.4% 的点击率，真正的素材效率很差。

**万象台官方文档：** CTR = 点击量 ÷ 展现量。所有「平均 CTR」都是按曝光加权的。

**结论：** 已按加权重写，4 月真实 CTR = 3.67%。**没有任何商业理由用算术平均。**

### ❌ 2. 关键词报表少灌 24K（ETL bug）

| 项 | 值 |
|---|---|
| 万象台后台关键词报表合计 | ¥35,810.20 |
| Dashboard 之前显示 | ¥11,518.30 |
| 缺口 | **¥24,291.90（缺 68%）** |

**根因：** ETL 去重 key 用了 `(日期, 词名字)`。但同一关键词「茶几」可以在「关键词推广」+「精准词包」+「自定义词包」**多个场景**下投放，第二个场景起整行被吞。

**结论：** 已改成 `(日期, 词ID, 场景名, 词名)` 4 维去重。重跑 ETL 后应该补回 24K。

## 二、需要你和店长**统一定义**的口径（每条都给两个选项 + 推荐）

### 🟡 3. GMV 的定义

万象台和生意参谋有 **3 套 GMV 口径**：

| 口径 | 字段 | 4 月值 | 含义 |
|---|---|---|---|
| **下单金额** | `order_amount` | 待算 | 拍下即记，含未付款、取消、退货 |
| **支付金额** | `pay_amount` | ¥219.5 万 | 实际付款，含退款前 |
| **净支付金额** | `pay_amount - refund_amount` | ¥149.6 万 | 扣完退款，最严 |
| **万象台总成交** | 直接+间接归因 | ¥106.4 万 | 推广引导（24h click）|

**推荐做法：**
- 核心 KPI 显示「**支付金额**」（行业通用）—— 219.5 万
- 旁边补「**净支付**」KPI —— 149.6 万（让大家看到退款的真实拉低）
- 「**下单金额**」放在「下单转化漏斗」分析专用，不作为对外汇报口径
- 「**万象台总成交**」只在投放面板用（算 ROI），不放总览（容易误以为是店铺 GMV）

**反对意见：**「下单金额是 GMV」不符合任何主流电商定义，会让对外汇报数虚高 25%+，建议放弃。

### 🟡 4. ROI 的分子分母——后台口径很拧巴

| 项 | 公式 | 4 月值 |
|---|---|---|
| 万象台后台 ROI | 总成交 ÷ **特定子集**花费 | **13.94** |
| 反推「特定子集花费」 | 1,063,569.47 ÷ 13.94 | ¥76,311 |
| 这 76,311 = ? | 商品级人群 38,647 + **全部**关键词 35,810 + 短视频 1,853 | ✓ 完全对得上 |

**关键发现：**
- 人群报表合计 64,375，但**只有 38,647 算入 ROI 分母**
- 差额 25,728 = 「人群推广里没归到具体商品的纯曝光花费」
- 这部分万象台**显示在人群报表里**，但**不计入 ROI 分母**——后台逻辑

**给店长的对账题：**
> Q: 投了 64,375 元的人群推广，为什么 ROI 只看 38,647 那部分？
> A: 因为另外 25,728 是「品牌词曝光位」「店铺侧边栏」这类没具体商品的位置。万象台默认这些是「品牌建设花费」不算转化分母。

**Dashboard 改动建议（已建任务 #33）：**
```
总投放 KPI 拆两层显示：
  - ROI 口径花费    ¥7.6 万   ← 和后台 ROI 对得上
  - 全曝光口径      ¥10.2 万  ← 含品牌曝光，决策预算用
```

### 🟡 5. 加购率——人维度还是件维度？

| 算法 | 公式 | 4 月值 |
|---|---|---|
| **人维度（推荐）** | `加购人数 / 访客数` | 40,295 / 438,631 = **9.19%** |
| 件维度 | `加购件数 / 浏览次数` | `cart_qty / page_views` |
| 错算可能 | `加购件数 / 访客数` | 会偏高，分子分母维度不一致 |

**为什么人维度更准：**
- 加购转化的本质是「访客变意向用户」的比例
- 件维度被「一人加多件」放大，反映的是已加购用户的兴趣深度，不是转化率
- 生意参谋官方「加购率」字段就是人维度

**店长如果坚持件维度：** 那应该叫「加购件数比」，且分母必须是 PV 不是 UV。

---

### 🟡 6. 转化率——同样的人/件之争

| 算法 | 公式 | 4 月值 |
|---|---|---|
| **支付转化率（推荐）** | `支付人数 / 访客数` | 7,861 / 438,631 = **1.79%** |
| 下单转化率 | `下单人数 / 访客数` | 通常比支付高 30%+（含未付款）|
| 件转化率 | `支付件数 / 访客数` | 受多件订单影响 |

**推荐：** 用「支付转化率」（人头去重），对应生意参谋 `pay_cvr` 字段。

---

### 🟡 7. 跳出率 / 停留时长——必须按访客加权

| 项 | 算法 | 影响 |
|---|---|---|
| **加权（推荐）** | `SUM(指标 × 访客数) / SUM(访客数)` | 真实店铺平均水平 |
| 算术平均 | 每商品取均值再平均 | 小流量商品被放大权重 |

**当前我们用加权（✓ 没问题）。** 跟店长再次强调：所有「均值类」指标都必须按真实样本加权，不能商品维度算术平均。

### 🟡 8. 上期对比——「等长前移」 vs 「上一完整周」

| 算法 | 当前周 4.27-30 → 上期 | 业务含义 |
|---|---|---|
| **等长前移（当前用）** | 4.23-26（前 4 天）| 周中投放看趋势 |
| 上一完整周 | 4.20-26（W17 全周）| 周报会复盘对比 |
| 同期年同比 | 2025-04-27 ~ 2025-04-30 | 季节性对比 |

**问题：** 现在投放面板用「等长前移」，但任务复盘可能习惯「上一完整周」。

**建议：** 让用户在 dashboard 顶部加一个切换按钮，三种对比模式可选。或者明确规定：
- 总览页 → 等长前移（看短期变化）
- 投放面板 → 上一完整周（对齐周报会）

**问店长：** 周报会复盘时你看的「上期」具体是哪种？

| 报表 | 4 月花费 | 含义 |

| 商品报表（商品级） | ¥51,513 | 投到具体 25 个主链 SKU 的钱 |

**目前 dashboard 显示：**

### 🟡 17. 直接成交 vs 间接成交（万象台归因）

万象台 GMV 分 3 块：
- **直接成交**：用户当次点击广告 → 直接下单（高确定性）
- **间接成交**：点击广告后 24h 内转化（通过其他入口）
- **总成交** = 直接 + 间接

**业务含义：**
- 直接成交占比高 → 广告素材直接转化能力强
- 间接成交占比高 → 广告主要起种草作用，最终成交在其他场景

**建议：** 投放面板加「直接 / 间接占比」分析，不要只看总成交（会误判素材效率）。

### 🟡 18. 含预售定金的处理

万象台说明：
> 当天实时数据**包含预售支付定金数据**，次日剔除。

**潜在问题：** 我们 ETL 是在凌晨拉前一天的数据，应该已经剔除了预售定金。但**预售活动期间**（双 11、618 等）的数字可能存在跨天波动。**HAY 当前主要是常态投放，影响小**，但大促时要警惕。

## 三、建议立刻验证的 5 个比例

跑一段 SQL 让 dashboard 数和这 5 个标准对得上：

```sql
WITH P AS (SELECT '2026-04-01'::text AS s, '2026-04-26'::text AS e),
agg AS (
  SELECT
    SUM(pay_amount)         AS gmv,
    SUM(visitors)           AS uv,
    SUM(cart_users)         AS cart_u,
    SUM(pay_new_buyers + pay_old_buyers) AS pay_buyers,
    SUM(pay_new_buyers)     AS new_buyers,
    SUM(refund_amount)      AS refund
  FROM fact_syzt_product, P WHERE stat_date BETWEEN P.s AND P.e
)
SELECT '加购率'         AS 指标, ROUND((cart_u     / NULLIF(uv,0)         * 100)::numeric, 2) AS my_value, 9.19  AS expected FROM agg
UNION ALL SELECT '支付转化率',     ROUND((pay_buyers / NULLIF(uv,0)         * 100)::numeric, 2),                    1.79  FROM agg
UNION ALL SELECT '新客成交占比', ROUND((new_buyers / NULLIF(pay_buyers,0) * 100)::numeric, 2),                    71.73 FROM agg
UNION ALL SELECT '退款率',       ROUND((refund     / NULLIF(gmv,0)        * 100)::numeric, 2),                    31.85 FROM agg
UNION ALL SELECT '客单价',       ROUND((gmv        / NULLIF(pay_buyers,0))::numeric, 2),                          279.23 FROM agg
ORDER BY 1;
```

5 行结果都 `my_value ≈ expected`（差额 < 5%）就是核心算法全对。

## 四、一锤定音的核心原则（建议写进部门 SOP）

1. **所有「均值类」指标必须按权重加权**——CTR、CPC、CPM、跳出率、停留时长、转化率，从来没有「商品维度算术平均」一说
2. **GMV 默认 = 支付金额，不是下单金额**，对外报表口径要统一
3. **「人维度」和「件维度」永远独立显示**，不要把分子分母维度搞混
4. **退款单独 KPI**，不能藏在 GMV 后面让人忘
5. **ROI 口径花费 ≠ 总投放预算**，要拆开看
6. **副 SKU 合并到主 SPU 的规则**由品牌方书面确认，存档到代码 SPU_MAP 注释里
